结论速览

主循环 agent-loop.ts:729 的 for (step = 0; ; step++) 本身是有界的（maxSteps 默认 64，外加 wall-time 上限），不会无限自转。用户感知到的"陷入循环"主要是三类真实故障叠加：

  1. 压缩后状态恢复失效 → 模型丢失"已做过什么"，反复重做同一段工作，进而反复触发压缩（最致命）。
  2. 强制压缩把近期上下文砍光 → 模型记忆进一步丢失，更易"迷路"；个别情况下直接 return 'failed' 让 turn 卡死。
  3. 会话存储无界递归 + 并发回写覆盖 → loadItems 在并发写入下反复重读/爆栈，工具结果偶发丢失又触发补调。

主循环控制流（确认有界）

agent-loop.ts:714  loop()
  for (step = 0; ; step++)                 // 退出条件：
    if (signal.aborted) return 'aborted'   //  ① 用户/系统中止
    if (step >= maxSteps) return 'failed'  //  ② 步数上限(默认64)
    if (wallTime >= maxWallTimeMs) ...     //  ③ 墙钟上限
    stepResult = modelStep(...)
    if (stepResult === 'stop')
        if (steering.sealIfEmpty(turnId)) return 'completed'  // ④ 任务完成
        else continue                     //   有未处理 steering → 再跑一轮
    if (failed / aborted) return ...       //  ⑤ 失败退出

循环表象不是来自这个 for，而是来自：模型持续返回 tool_calls（直到 64 步耗尽），或上下文被压缩后重做导致 step 被无效消耗。

修复优先级建议

① 接通压缩状态恢复（消除"重做循环"，收益最大）

  • 在 runtime-event-reducer.ts:278 applyCompactionEvent 中把 event.stateRecovery 存进 projection（新增 projection.compactionRecovery 或塞进 compaction item 的字段）。
  • 在 model-step-service.ts:440 附近组装 contextInstructions 时，读取最近一次 compaction 的 stateRecovery 并追加为一条 system instruction（例如："## 之前会话状态 (压缩后恢复) … 不要重做已完成的工作"）。
  • 这样模型压缩后仍保留"已改文件/最近错误/用户原始意图"，不会重复劳动。

② 把 loadItems 递归改为有界重试（消除崩溃/卡顿）

  • file-session-store.ts:252 改为 for (let retry=0; retry<3; retry++) { ... if (version 一致) return 快照; }，超过上限返回当前读到的快照（并打 warn 日志），不要递归。

③ 软化强制压缩的激进程度

  • model-step-service.ts:621 的 force 压缩不要把 keepRecent 一直设为 1；可在连续 force 时保留更多 tail（如 keepRecent 2~4），避免把"刚发生的对话"裁掉。
  • 或在 context-compactor.ts:170 的 noop 分支直接返回，避免无效落盘。

④ 增强停止判据（可选）

  • 当 ToolStormBreaker 连续抑制且模型仍试图调用时，把 round outcome 导向 stop 而非继续消耗 step。
  • 降低只读重复阈值（15 → 8 左右）或改用"参数相似度"而非"参数全等"判定。
